\section*{Intro}

\begin{frame}{Motivation for B-Trees}
\begin{itemize}[<+->]
  \item
    Index structures for large datasets cannot fit \\in main memory.
  \item
    Disk and SSD storage require a different approach \\to efficiency.
  \item
    Modern SSDs have random access times of \\approximately 100--200 microseconds.
  \item
    One SSD access takes more time than 500,000--2,000,000 \\CPU instructions (on modern multi-GHz processors).
  \item
    One SSD access is approximately 1,000--10,000 times slower \\than reading from main memory (50--100 ns).
\end{itemize}
\end{frame}

\begin{frame}{Motivation for B-Trees}
\begin{itemize}[<+->]
  \item
    Suppose an \href{https://en.wikipedia.org/wiki/AVL_tree}{AVL tree} is used to store 20 million \\records on an SSD.
  \item
    This very deep binary tree requires lots of SSD accesses;\\
    \(\log_2{20,000,000} \approx 24\) accesses \(\times 150\) \\microseconds per access \(\approx 2.6\) milliseconds.
  \item
    We know we can't improve on the \(\log_2{n}\) lower bound on the search for a binary tree.
  \item
    The solution is to use more branches and, thus, reduce the tree height!
  \begin{itemize}
    \item
      As branching increases, depth decreases, so fewer expensive storage accesses are needed.
  \end{itemize}
\end{itemize}
\end{frame}

\begin{frame}{Realistic Worst-Case Scan}
You need to scan all records in a 1-billion row table.\\
Assume each random access is \(150\) microseconds.

\pause{}
\begin{itemize}[<+->]
  \item AVL/BST lookup per key: \(\approx 30\) random reads (height \(30\)).
  \item AVL I/O time: \(1{,}000{,}000{,}000 \times 30 \times 150\mu{}s \approx \mathbf{52}\) \textbf{days}\\ (or \(75\) minutes at \(1{,}000\times{}\) parallelism).
  \item B-tree (order \(101\)) height: \(\approx 5\); therefore, \(5\) reads/key.
  \item B-tree I/O time: \(1{,}000{,}000{,}000 \times 5 \times 150\mu{}s \approx \mathbf{9}\) \textbf{days}\\ (or \(12.5\) minutes at \(1{,}000\times{}\) parallelism).
\end{itemize}

\pause{}
\textbf{Takeaway}: Even with parallelism, reducing tree height from 30 to 5 saves \(6\times{}\) I/O work. This is why B-Trees dominate for large datasets.
\end{frame}

\begin{frame}{Web Search Scale}
Live system: \(10,000\) queries/sec,\\
each needs one key lookup in \(8.5\)B pages.

\pause{}
\begin{itemize}[<+->]
  \item AVL tree depth: \(\approx 33\). \(33\) \\
    SSD accesses/query = \(4.95\) ms/query at \(150\mu{}s\)/access.
  \item B-tree height (order \(101\)): \(\approx 4\). \(4\) \\
    SSD accesses/query = \(0.6\) ms/query.
  \item 10k q/s: AVL = \(49.5\) seconds of SSD work per second (queueing backlog).\\
    B-tree = \(6\) seconds of SSD work per second.
\end{itemize}

\pause{}
AVL-style access causes user-visible stalls under load,\\
while a B-tree design maintains low-latency response.
\end{frame}

\begin{frame}{Definition of a B-tree}
  A B-tree of \emph{order} \(m\) is an \(m\)-way tree (i.e., a tree where \\each node may have up to \(m\) children) in which:\pause{}

    \begin{enumerate}
      \item<+->
        All leaves are on the same level.
      \item<+->
        The number of children of a non-leaf node is always one more than the number of keys.
      \item<+->
        The keys of a node are sorted in increasing order. These keys partition the child keys as a search tree.
      \item<+->
        The root is either a leaf node or has two to \(m\) children.
      \item<+->
        Other non-leaf nodes have at least \(\left\lceil {m / 2} \right\rceil\) children.
      \item<+->
        A node contains no more than \(m - 1\) keys.
    \end{enumerate}
    \onslide<+->{The number \(m\) should always be odd.}
\end{frame}

\begin{frame}{Constructing a B-Tree}
\begin{itemize}[<+->]
  \item
    Attempt to insert the new key into a leaf.
  \item
    If this would result in that leaf becoming too big, split the leaf into two, promoting the middle key to the leaf's parent.
  \item
    If this would result in the parent becoming too big, split the parent into two, promoting the middle key.
  \item
    This strategy may need to repeat to the root.
  \item
    If necessary, the root is split in two and the middle key is promoted to a new root, making the tree one level higher.
\end{itemize}
\end{frame}

\section{Deletion}

\begin{frame}{Deletion from a B-Tree}
  \center{}\large
Key are always inserted \emph{into leaves}.

For deletion, we wish to remove \emph{from a leaf}.

There are four deletion cases to consider in order.
\end{frame}

\begin{frame}{Cases for Deletion from a B-Tree}
\begin{enumerate}
  \item<+->
    \textbf{Key is in a leaf}:\\ Delete the key.
  \item<+->
    \textbf{Key is not in a leaf}:\\ Its predecessor and successor must be in leaves. Delete the key and promote either the predecessor or successor (implementor's choice) to replace it in the non-leaf position.
\end{enumerate}

\pause{}
After performing Case 1 or 2, a leaf node may now have too few keys (\emph{underflow}). We will fix this underflow with Case 3 or 4.
\end{frame}

\begin{frame}{Cases for Deletion from a B-Tree}
When removing a key would cause \\
\textit{underflow} (too few keys), handle it as follows:

\begin{enumerate}
  \setcounter{enumi}{2}
  \item<2->
    \textbf{Sibling has spare keys --- Rotate}:
    \begin{itemize}\small
      \item Pull a key from a sibling up to the parent.
      \item Demote the parent key down into the lacking leaf.
    \end{itemize}
  \item<3->
    \textbf{Neither sibling has spare keys --- Merge}:
    \begin{itemize}\small
      \item Combine the lacking node, sibling, and parent key into one node.
      \item If the parent now underflows, recursively apply Cases 3 or 4 to it.
    \end{itemize}
\end{enumerate}
\end{frame}

\begin{frame}{Maximum Keys in an Order-\(m\) B-Tree}
  \begin{columns}
    \column{0.3\textwidth}%
    Max keys per level:\\
      \begin{tabular}{c c}
        \toprule
        Level & Key Count\\
        \midrule
      root    & \(m - 1\)\\
      \(1\) & \(m^1(m - 1)\)\\
      \(2\) & \(m^2(m - 1)\)\\
      \(\vdots\) & \multicolumn{1}{c}{\(\vdots\)} \\
      \(h\) & \(m^h(m - 1)\)\\
      \bottomrule
      \end{tabular}
  \column{0.7\textwidth}\pause{}
    So, the maximum number of items is:
    \begin{align*}\vspace{-1em}
      t &= (1 + m + m^2 + m^3 + \cdots + m^h)(m - 1)\\
        &= \frac{m^{h+1} - 1}{m - 1} (m - 1)\\
        &= m^{h+1} - 1
    \end{align*}
  \end{columns}\vspace{1em}
  \pause{}
  When \(m = 5\) and \(h = 2\), this gives \(5^{2 + 1} - 1 = 125 - 1 = 124\).
% \end{itemize}
\end{frame}

  \begin{tabular}{l l l}
    \toprule
      \textbf{Operation} & \textbf{Balanced Binary Tree} & \textbf{\(m\)-Way B Tree}\\
    \midrule
      Insert   & \onslide<2->{\(O(\log_2{n})\)} & \onslide<5->{\(O(\log_2{n})\)} \\
      Find     & \onslide<3->{\(O(\log_2{n})\)} & \onslide<6->{\(O(\log_2{n})\)} \\
      Delete   & \onslide<4->{\(O(\log_2{n})\)} & \onslide<7->{\(O(\log_2{n})\)} \\
    \bottomrule
  \end{tabular}
\end{table}
}
\vspace{1em}
\onslide<8->{
  The benefits are:
  \begin{enumerate}
    \item 
      Reduced hard-drive access (but the same number of instructions) and 
    \item 
      Reduced memory usage (fewer pointers).
  \end{enumerate}
}

\begin{frame}{Reasons for Using B-Trees}

When searching tables held on a hard drive, the cost \\
of each drive transfer is high but doesn't depend much \\
on the amount of data transferred, especially if \\consecutive items are transferred.

\begin{itemize}
    \item
      For example, an order 101 B-tree can transfer each node in one drive read operation.
    \item
      An order 101 B-tree and height 3 can hold \(101^4 - 1\) items (approximately 100 million) and any item can be accessed with 3 drive reads (assuming we hold the root in memory).
\end{itemize}
\end{frame}

\begin{frame}{Reasons for Using B-Trees}
If we take \(m = 3\), we get a \emph{2--3 Tree}, in which non-leaf\\
nodes have two or three children (i.e., one or two keys).
\begin{itemize}
  \item
    B-Trees are always balanced (since the leaves are all at the same level), so 2--3 Trees make a good type of balanced tree.
\end{itemize}
\end{frame}

\begin{frame}{Comparing Trees}
\begin{itemize}[<+->]\large
  \item
    Binary trees
    \begin{itemize}
      \item
        Can become \emph{unbalanced} and lose their good time \\complexity (Big \(O\)).
      \item
        \emph{AVL Trees} are strict binary trees that \emph{overcome the balance problem}.
      \item
        Heaps remain balanced but are unsorted.
    \end{itemize}
  \item
    Multi-way trees
    \begin{itemize}
      \item
        B-Trees are \(m\)-way, with any (odd) number of children.
      \item
        The 3-Way B-Tree (a.k.a 2--3 Tree) approximates a self-balancing binary tree, exchanging the AVL tree's balancing operations for insertion and (more complex) deletion operations.
    \end{itemize}
\end{itemize}
\end{frame}

\section{Variations}

\begin{frame}{Introduction to B*-Trees}
  B*-Trees are a B-Tree variant that increases node\\ occupancy for better space utilization.

  \pause{}
  \begin{itemize}[<+->]
    \item B*-Trees require non-root nodes to be at least \(2/3\) full\\ (vs. \(1/2\) full in B-Trees).
    \item Insertions may redistribute keys among siblings before splitting, reducing splits overall.
    \item This typically yields denser nodes and fewer I/O operations in large storage systems.
    \item B*-Trees preserve B-Tree search costs while improving storage efficiency.
  \end{itemize}
\end{frame}

\begin{frame}{Introduction to B+Trees}
  B+Trees are a variant of B-Trees that further optimize for disk-based storage and range queries.

  \pause{}
  \begin{itemize}[<+->]
    \item All data (or pointers to data) are stored only in leaf nodes.
    \item Internal nodes store only keys (no records); therefore, they can hold more keys.
    \item Leaf nodes are linked sequentially, enabling fast full-range scans and ordered iteration.
    \item Higher fan-out and fewer disk reads per access make B+Trees popular in databases and file systems.
    \item Insertion and deletion keep leaves at the same depth, preserving strong balance and performance.
  \end{itemize}
\end{frame}

\begin{frame}{Advanced B-Tree Variations}
  Beyond B+Trees and B*-Trees, researchers and systems developers have created specialized variants:

  \pause{}
  \begin{itemize}[<+->]
    \item \textbf{B\textepsilon{}-Trees}: Write-optimized variants with buffered\\ internal nodes to batch insertions, useful for heavy\\ write workloads in key-value stores.
    \item \textbf{B-Link Trees}: Concurrency-friendly variants with sibling pointers and latch-free search paths, common in database index implementations.
    \item \textbf{Cache-aware/Cache-oblivious B-Trees}: Variants optimized for modern memory hierarchies (L1/L2/L3 caches) rather than just disk I/O.
  \end{itemize}
\end{frame}
